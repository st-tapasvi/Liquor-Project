> Self-contained context for anyone (person or AI) starting work on this codebase. Read this first, then `02-backend-architecture-standards.md` for the rules and `03-solution-structure.md` for where things are.
> Version 2.0 — 2026-09-25. Supersedes `project-overview-brief.md` (2026-09-18).

## 1. What the product does

Track & trace software for **liquor (excise) manufacturing in India**. Every bottle and case produced in a distillery must be marked, scanned, aggregated (bottle → case), and reported to that state's excise department.

Two pieces of software run at a plant:

| | Runs where | Does what | In this solution as |
|---|---|---|---|
| **Line application** | Desktop PC on the bottling line | Cameras, OpenCV decode, label printers, PLC. Prints case labels, scans bottles, aggregates bottle → case. | `ST.LiquorTNT.Desktop` (WinForms) |
| **Server application** | Server PC at the plant | Masters (company, brand, batch, users), case code generation/allocation, reports, push to the state excise portal. | `ST.LiquorTNT.Api` + React `ST.LiquorTNT.WebApplication` |

The line application stays on the desktop (hardware) but **stops touching the database directly** — it consumes a **Line API** (`/api/line/...`) from the new server.

## 2. The problem being solved

Today there are **11 separate state-wise server applications** — all C# WinForms, each with its own database:

`UP RJ MP JK DL CG AS HP TN KL MG`

They drifted apart through copy-paste. We are replacing all of them with **one platform** that serves every state at runtime through configuration — explicitly **not** 11 apps in one repo.

Agreed principle: **~80% common core + ~20% per-excise capability.** State differences are implemented as small per-state components behind narrow interfaces (`IBrandProvider`, `ICaseCodeGenerator`, `IBottleCodeValidator`, `IPortalProcessor`, `IDispatchProcessor`, `IExciseRules`), resolved by excise code. `if (excise == "RJ")` in common code is a defect.

## 3. Where the states actually differ

1. **Source of master data** — typed (DL, MP), read from the excise's own DB (JK), portal API (RJ eConnect, CG NIC, TN TASMAC, UP OASYS, HP C-Tel), or portal Excel import (DL, UP).
2. **Source of the case code** — generated by us (DL = SSCC-18, RJ = 28-digit, MP = per-brand 8-digit sequence) or allocated by the portal (UP per plan, TN per batch).
3. **Source of the bottle code** — printed by us, downloaded, or state-issued pre-printed hologram with a serial range to validate (MP, CG).
4. **What goes to the portal** — Excel, XML, one file per case, HTML, or live API push (CG, UP, HP, TN). Regenerate and undo required.
5. **Brand identifier** — GTIN (DL, UP), ETIN (MP), Label/Unit ID (JK, CG), Brand Code + Packing Code + MRP (RJ family).
6. **Validation limits** — e.g. carton height 50–350 mm (JK) vs 50–400 mm (MP). These are **database configuration values**, not code.
7. **Modules only some states have** — Dispatch (CG full workflow; MP undocumented), Palette (UP, CG), Plan (UP), code-pool download (UP, TN).
8. **Product hierarchy depth** — JK is Brand → Label → Unit; DL/UP/MP are flat Brand + pack size.

## 4. Tenancy and deployment

- **Customer** = distillery. One plant can produce for **several states**; one installation can hold **several companies**. Tenancy is **Company → Plant → Excise**, and all three come **only from the JWT** (`company_id`, `plant_id`, `excise_code`) — never from a request.
- **Everything runs on the customer's own server (on-premise)**: one API, one database, one React build served from the same host. Often no IT staff, sometimes no internet.
- Multiple production lines write into the same local API simultaneously.

## 5. Scale and constraints

- Peak ~**100,000 cases/day ≈ 4,800,000 bottles/day** per plant → **1.5+ billion bottle rows/year**. Time partitioning and archival are mandatory; nothing loads a transaction table into memory.
- Portal or internet may be down — **production must never stop**: local write first, outbox row in the same transaction, background worker pushes and retries.
- Planned life **15+ years**. Maintainability, auditability and configurability rank above short-term speed.

## 6. Technology — locked

**Backend**

| | |
|---|---|
| Runtime | .NET 8 LTS, C# latest, `nullable enable`, warnings-as-errors in Release |
| Style | Modular monolith, Clean Architecture: `Api → Business → Domain`, `Infrastructure` implements Business interfaces |
| Database | **MySQL 8 primary** (`st_tnt_liquor`), **SQL Server supported** via `Database:Provider`. One customer runs one. SQL Server Express is a non-starter (10 GB cap). |
| Data access | EF Core 8 (Pomelo for MySQL); **SPs, views and triggers used freely** where the use case calls for them, scripts per provider under `Infrastructure/Database/Scripts/<Provider>/`. Views preferred for anything that must still filter/page (LINQ composes over a view, not over an SP). |
| API shape | REST, **no version segment** (one build per plant), RFC 7807 ProblemDetails for errors, plain payload for success |
| Auth | JWT bearer for web; machine key + numeric PIN for the line (separate scheme, later). PBKDF2-SHA256 passwords, lockout after 3 |
| Validation / Logs / Tests | FluentValidation · Serilog (3 streams: application, audit/user-log, integration; normal vs detail mode) · xUnit + FluentAssertions + NetArchTest (+ Testcontainers later) |

**Frontend** — React 18 + TypeScript strict, Vite, React Router v6, TanStack Query v5, Zustand, Axios, MUI v6 + DataGrid, react-hook-form + zod, orval-generated client from the API's OpenAPI. Feature-sliced: `app → features → entities → shared → core`. **No excise literals in UI code** — per-state differences arrive as screen configuration and feature flags from the API. Details in `frontend-architecture-standards.md`.

## 10. How the login request travels (the pattern every module follows)

```
POST /api/auth/login  { userName, password }
  Api          AuthController.LoginAsync            → calls IAuthService
  Business     AuthService.LoginAsync               → LoginRequestValidator (FluentValidation)
                                                    → IUserRepository.GetByUserNameAsync
                                                    → IPasswordHasher.Verify
                                                    → user.RegisterFailedLogin(3) / RegisterSuccessfulLogin   (Domain rule)
                                                    → IAccessTokenService.Create
  Infrastructure  UserRepository (EF Core, AppDbContext) · Pbkdf2PasswordHasher · JwtAccessTokenService
  Api          ExceptionMiddleware turns any AppException / DbException into ProblemDetails with errorCode + correlationId
  ← 200 { accessToken, expiresAtUtc, user{...} }
```

Interfaces `IUserRepository` and `IAccessTokenService` are **declared in `Business/Auth/`** (the feature that owns them) and **implemented in `Infrastructure`**. Domain declares no interfaces.
